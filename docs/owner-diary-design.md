# 主人日记设计稿

状态：1.2.0 已实现；实际配置、权限和边界见 [主人日记使用说明](owner-diary.md)。现有查询保留，日记独立且默认关闭。

## 上游已有的查询能力

已核对 Monika-Dream/live-dashboard：`main` 提交 `6ba9a5edc09b0c4389d1d6b57a4f55ff385d855b`，花信分支 `redesign/blossom-letter` 提交 `196aed8819dedc23ca8675379af74613a3c7aa18`。

- 两个分支均有 `/api/current` 和按日期、时区查询的 `/api/timeline?date=YYYY-MM-DD&tz=-480`（此偏移示例表示 UTC+8）。已有历史查询不依赖插件日记或麦麦原生长期记忆。
- 花信分支另有 `/api/daily-summary?date=YYYY-MM-DD`，返回 `date`、`summary`、`generated_at`；未生成时后两个字段为 `null`。`main` 分支没有该路由。
- 花信小结需配置服务端 AI 端点和密钥，生成目标为约 50–80 字。当前调度按服务进程时区在 21:00 尝试生成当天小结；21:00 之后的数据不会自动补进已生成正文，不宜直接称为完整自然日的最终日记。
- 当前活动记录按写入时间清理 7 天前的数据，每小时检查；花信日总结表也有按日期清理 7 天前记录的逻辑。具体部署如果修改过源码，应以部署版本为准。
- `live-dashboard-agent.exe` 是设备上报客户端，插件读取的是已部署的面板服务，不能把客户端的 Release 下载地址当成查询地址。

因此实现应先复用已有接口，避免重复建设活动历史。需要最近活动时直接查时间线；上游已有小结且内容符合日记权限与隐私范围时，可以直接读取或归档，不必重复调用模型。归档必须标明生成时间，不能将 21:00 小结描述为包含整天活动。完整日汇总和超过上游保留期限的长期保存，才需要下面的日记流程。

上游小结是一个混合生成的文本，不能在本地可靠拆分设备和字段。若其内容可能超出当前允许范围，不使用该小结，改从经过过滤的结构化时间线生成。日记是否长期归档、是否补充晚间活动，由独立设置控制，不因检测到接口就自动开启。

## 目标

每天结束后，将配置面板中前一天的设备活动整理成一篇可回看的主人日记。麦麦可以按日期读取这些日记，用于回答“主人昨天忙什么”“最近几天在做什么”。身份称呼继续来自麦麦人设；插件不推断或重写主人身份。

日记以麦麦观察主人的视角写作，使用第三人称，文字自然、简短。设备记录不能证明的工作成果、心情、作息、饮食和动机不进入正文。例如，编辑器活动可以写成“电脑记录到编辑器使用”，不能推断“完成了项目”；游戏运行也不能证明主人全程在玩。

## 日界线与调度

- 独立开关，默认关闭。启用日记不同时启用后台实时观察、Prompt 注入或主动聊天。
- 默认时区 `Asia/Shanghai`，默认次日 `00:15` 汇总前一自然日，为延迟上报留出时间。
- 日期范围按所选时区的两个相邻午夜计算；跨午夜片段只取目标日内部分。不能按进程时区或固定加 24 小时替代。
- 优先直接读取面板已有的指定日期时间线，不要求插件全天轮询。插件未运行期间能否补齐，取决于面板是否保存了相应历史。
- 任务按“面板来源 + 日期 + 时区”去重。配置重载、重启和并发触发不会产生重复日记。
- 重启后最多检查前 3 天缺失任务，逐日串行补齐；只在该来源启用日记之后的日期范围内自动补录。更早的日期由用户明确请求。
- 请求失败保留失败状态并有限重试；没有数据与获取失败分别记录。没有活动数据时生成事实说明，不调用模型补写经历。
- 自动生成成功后不反复重写。面板后续补报数据时，用户可以请求重新生成；依据输入指纹判断是否发生变化，保留修订信息。

## 输入与事实整理

读取 `/api/timeline` 的结构化 `segments` 和 `summary`，不要先调用聊天渲染器再把其输出交给模型。现有渲染器有展示片段上限，直接拿展示文本做全天日记可能漏掉后半天。

处理顺序：

1. 检查返回结构、日期和时间单位；标记接口明确声明的分页或截断。没有覆盖信息时不声称掌握了完整一天。
2. 按日记专用设备范围和现有敏感信息规则过滤，在写入磁盘和调用模型之前移除不允许保留的内容。
3. 将时间片段裁剪至目标日；剔除异常时长，合并同设备的相邻重复活动。无结束依据的记录不任意延长到午夜。
4. 按设备统计应用时长，并保留少量主要活动和时段。不同设备可能同时使用，不能将其时长相加称为主人的总活动时间；如计算跨设备覆盖时长，使用已知区间的并集。
5. 保存规范化事实、来源、时间范围和缺口说明。覆盖范围不明、只有汇总没有片段等情况明确标注，不虚构覆盖率。
6. 通过代码压缩相同活动和细碎片段，尽量控制模型材料体积；如仍需舍弃片段，记录摘要输入不完整，保留主要统计事实。

默认只保留允许设备的应用名称与必要的时间、时长。窗口标题和健康数据默认不进入日记；好友面板、服务健康指标不混入主人日记。设备在线、应用运行与人实际参与保持区别，设备离线不解释成睡觉。

现有设备名称过滤主要作用于实时状态。日记实现必须在自己的输入链路执行设备范围过滤，不能假定时间线服务已经完成相同处理。

## 自然语言生成

- 事实整理由代码完成，模型负责基于事实写一段约 200–400 字的日记。
- 优先使用官方 `ctx.maisaka.reply.generate`，复用指定已有聊天流的人设和 Replyer 链路。该能力返回文本，不自动发送，也不需要先触发一轮群聊。
- 日记生成会话必须显式配置为已有聊天流；不能通过人设中的主人称呼自动猜测账号或创建会话。没有合适会话或能力不可用时，保留程序生成的事实版，不隐式切换到额外模型服务。
- 模型材料只包含经过过滤的当日事实和必要写作约束；应用、标题等外部字段作为数据处理，不执行其中的指令。
- 数值统计、时间范围和来源由程序生成的事实区承载。模型不得添加新活动、未提供的精确时间和时长，也不得把使用工具直接写成已取得成果；校验或生成失败时退回事实版，保留错误状态。
- 常规情况每天执行一轮日记生成，失败重试受限。官方 Replyer 流程可能包含额外表达选择等调用，不能承诺底层每天严格只有一次模型请求。

## 存储与读取

- 每篇包含结构化事实和可阅读正文两部分，放在插件持久化目录；Markdown 可以作为导出格式。
- 元信息至少包括：日期、时区、面板来源标识、生成时间、输入指纹、版本、生成状态、数据缺口说明。
- 按面板来源隔离日记；更换面板配置不能把旧主人的日记当成新来源活动。持久化文件不包含认证令牌。
- 默认保留 90 天，支持按日期删除、全部清除和导出。变更隐私过滤策略后，先使旧日记不可供模型读取，再选择清除或从允许的原始事实重建；不能只对新采集数据应用规则。
- 新增按日期或小范围日期查询的模型工具。只有经授权的用户、会话可读取；读取白名单为空时不向聊天提供日记，历史资料不自动继承实时状态的公开范围。
- 查询“昨天/上周”时读取相应日记；查询“现在”时仍调用实时状态工具。日记日期与生成日期分别展示，不混淆昨日和今日。
- 日记内容通过工具交给 Planner，由其将相关事实放入原生 `reply_reference`，最后由 Replyer 自然回答。不把全部历史日记塞进每轮 Prompt。
- 人物身份取自人设，但日记的读取权限、生成会话需要显式配置，不能靠模型判断是否为主人来鉴权。

## 与记忆、主动聊天的关系

持久化日记首先是插件自己的可检索历史资料，不等于已写入 A_Memorix 原生长期记忆。未来需要原生记忆集成时，单独对接实际可用的写入接口，带来源、日期、人物归属和去重标识，并支持删除、修订后的同步失效；不靠伪造用户发言或追加上下文保证入库。

日记生成和日记推送分别控制。第一版生成后安静保存；读取日记不会自动开启主动发言。以后如果允许麦麦主动提起日记，仍需经过会话范围、免打扰、有效期、去重和触发预算检查，通过官方主动任务提出意图，不强制逐字发送正文。

## 建议初始配置

| 设置 | 建议值 |
| --- | --- |
| 每日日记 | 关闭，手动启用 |
| 时区 | Asia/Shanghai |
| 汇总时间 | 次日 00:15，汇总前一天 |
| 自动补录上限 | 前 3 天且不早于启用日期 |
| 保留期限 | 90 天 |
| 生成会话 | 显式配置的已有聊天流 |
| 窗口标题 / 健康数据 | 不收集 |

| 原生长期记忆写入 | 第一版不启用 |

## 实现验收

- 本地日期、跨午夜片段和时区改变正确；不同设备重叠不会夸大人的活动时长。
- 日记材料覆盖接口返回的允许数据，不受聊天展示条数上限影响；上游缺失或截断如实标记。
- 重启、重载、重复任务和网络重试不会重复生成；后台关闭后不继续提交新生成任务或保存过期配置的结果。
- 同日重新生成有输入变化检查和明确修订记录；无数据、网络失败、模型失败可区分。
- 过滤在持久化和模型调用之前完成；历史读取也受授权和策略变更影响。
- 不生成数据源没有支持的心情、成果或离线期间经历。
- 生成任务不发送聊天消息，不追加伪造用户消息，不自动修改 Prompt 或原生长期记忆。
